Building a tiny queue worker in plain JavaScript

A Northgrove Dev Guild tutorial · about ninety minutes · Node.js 22 or later

1 Why a queue at all?

Most web applications eventually have work that should not happen while a visitor waits: sending a receipt, resizing an uploaded photo, calling a slow partner service. The usual answer is a job queue. The request handler writes a small description of the work into the queue and returns at once; a separate worker process picks the job up a moment later and does the work in its own time.

There are excellent queue libraries, and for a production system you should probably use one. This tutorial builds a very small queue from scratch anyway, because doing so teaches the three ideas every queue has to get right: jobs must not be lost when a process crashes, a failing job must be retried without being retried forever, and a worker must be able to stop without abandoning the job in its hands. We store the queue in a single JSON file, which is slow and only works for one worker, but it keeps every moving part visible.

You will create three files in an empty directory: queue.js, worker.js and handlers.js. No packages need to be installed; everything used here ships with Node.

2 Loading the queue

Start with the smallest useful piece: a function that reads the queue file and returns the list of jobs. If the file does not exist yet, the queue is simply empty. Any other error, such as a file that is not valid JSON, is thrown, because silently starting with an empty queue would discard every job in it.

Listing 1. A first version of loadQueue

import { readFile, writeFile, rename } from "node:fs/promises"; const QUEUE_FILE = "jobs.json"; export async function loadQueue() {  try {    return JSON.parse(await readFile(QUEUE_FILE, "utf8"));  } catch (error) {    if (error.code === "ENOENT") return [];    throw error;  }}

Notice that the error check compares error.code with the string "ENOENT" rather than looking at the message. Error messages are written for people and may change between versions of Node; error codes are part of the interface.

3 The complete queue module

The full module adds four operations: putting a job in, choosing the next job to run, claiming it, and updating it when it finishes. The most important detail is in saveQueue. It never writes the queue file directly. Instead it writes a temporary file and then renames the temporary file over the real one. On every mainstream file system a rename within one directory is atomic: other processes see either the old file or the new one, never a mixture.

The listing below is the whole module, seventy-six lines. It is printed in one piece on purpose, so that you can read it top to bottom before we take it apart.

Each job records how many times it has been attempted and how many attempts it is allowed. The runAfter field is a timestamp before which the job must not run; new jobs are runnable immediately, and retried jobs are pushed into the future by the worker’s backoff rule. nextRunnable picks the job that has been waiting longest, which gives a rough first-in, first-out order without any extra bookkeeping.

4 The worker

The worker is a loop: claim a job, run its handler, record the result, repeat. When there is nothing to do it sleeps for a second and asks again. That polling interval is the price of storing the queue in a plain file; a queue backed by a database or a message broker can wake the worker the moment a job arrives.

Two parts of the worker deserve a closer look. The retry rule doubles the waiting time after each failed attempt, starting at two seconds and capping at five minutes, so that a job which fails because a partner service is down does not hammer that service every second. And the signal handler lets the worker stop gracefully: the first SIGTERM sets a flag that ends the loop after the current job, and only a second signal exits immediately.

The recover function at the end handles the case the graceful stop cannot: a worker that was killed outright, by a power cut or an out-of-memory error, leaves its job in the running state forever. Resetting such jobs at start-up means they run again. That is only safe if handlers are written so that running them twice does no harm, which is the subject of the next section.

5 Handlers and idempotence

A handler is an asynchronous function that receives the job’s payload. The example handlers below are deliberately trivial. The flaky handler is useful for watching the retry rule at work: enqueue it with a failUntil time a minute in the future and follow the log.

Listing 4. handlers.js

// handlers.js: the jobs this example knows how to runimport { appendFile } from "node:fs/promises"; export const handlers = {  async "write-note"({ text }) {    if (typeof text !== "string" || text.length === 0) {      throw new Error("write-note needs a non-empty 'text'");    }    await appendFile("notes.txt", text + "\n", "utf8");  },   async "flaky"({ failUntil }) {    // Fails until the given time, then succeeds: useful for testing retries.    if (Date.now() < failUntil) throw new Error("not yet");  },   async "slow"({ ms }) {    await new Promise((resolve) => setTimeout(resolve, ms));  },};

Because a job can run more than once, real handlers should be idempotent: running them twice should have the same effect as running them once. Sending an email is the classic counterexample. The usual remedy is to record, before doing the work, that the work is about to happen, and to check that record at the start of the handler.

6 Where to go from here

You now have a queue that survives crashes, retries with backoff and stops cleanly. It will not scale beyond one worker, because two workers could claim the same job between reading and writing the file. Fixing that needs a lock, and at that point it is time to move the queue into a database that provides one. The structure of the worker stays exactly the same.
